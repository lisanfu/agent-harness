## 2. 一句话总结

这本书讨论的不是怎样让 Agent “显得聪明”，而是怎样让 Agent 在真实环境中**可执行、可恢复、可观测、可约束、可验证**。它把 Agent 当成一个需要运行时、状态管理、故障治理和安全边界的工程系统，而不只是一段 Prompt。

全书的核心问题是：为什么 Demo 经常成功，生产环境却经常失败？

## 3. 内容定位

官方简介重点关注以下生产故障：

- 无限循环。
- 幻觉与静默失败。
- 上下文溢出。
- 工具调用失控。
- 资源耗尽。
- 多 Agent 级联故障。

对应的工程主题包括执行编排、容错恢复、状态管理、安全边界、可观测性和成本控制。

适合的读者包括 Agent 开发者、AI 应用工程师、后端工程师、架构师、平台与运维人员，以及希望理解 Agent 可靠性边界的普通使用者。

## 5. 逐节详细内容

本节按官方完整目录展开全部 **54 个小节**。每节区分两层信息：“目录覆盖”忠实列出官方页面公开的小标题；“阅读重点”和“工程意义”是依据这些标题做的导航式解读，不代表作者原文，也不等于已经读过正文。阅读正文时，可以用这些内容检查自己是否抓住该节的问题、方法与边界。

### 第 1 章 Agent 的“第一次”危机

#### 1.1 一个真实的失败案例

**目录覆盖**：从一个真实失败案例切入 Agent 的可靠性问题。

**阅读重点**：不要只记“Agent 失败了”，而要还原任务起点、模型判断、工具调用、环境反馈和最终结果。特别留意失败是单点故障，还是前面某个错误决策不断放大的结果。

**工程意义**：真实案例适合被改写成一条可重放的故障 trace，再转成回归测试。对工程团队而言，“发生了什么”之后还必须回答“哪一步开始错”“为什么系统没有及时止损”“相同输入现在能否复现”。

#### 1.2 生产环境的第一课：什么会出错

**目录覆盖**：API 调用的失败维度、工具调用的失败场景、状态管理的失败陷阱。

**阅读重点**：API 失败不只是超时，还可能表现为限流、鉴权失效、响应结构变化、长尾延迟或错误被包装成正常文本；工具失败不只是抛异常，还可能返回不完整结果、产生部分副作用或悄悄跳过步骤；状态失败则涉及并发覆盖、过期状态、恢复错位和信息丢失。

**工程意义**：这三类问题分别对应外部依赖、执行器和状态机。生产系统必须为它们设置不同的错误分类和处置策略，不能把所有异常都交给模型“再想一想”。

#### 1.3 Agent 系统崩溃的六大模式

**目录覆盖**：无限循环、上下文溢出、输出格式失控、资源耗尽、级联失败、静默失败。

**阅读重点**：六种模式要放在一起看：循环消耗调用预算，上下文增长加剧模型退化，格式错误可能触发重试，资源耗尽又诱发下游超时，最后多个故障级联；静默失败最危险，因为系统看起来仍在运行，却没有产出正确结果。

**工程意义**：每种模式都应有独立于模型的硬边界，例如最大步数、token 预算、解析器、并发与磁盘上限、调用链断路、独立结果验证。不能指望 Prompt 自觉避免全部六类故障。

#### 1.4 为什么 Demo 总是成功，而生产总是失败

**目录覆盖**：输入的可控性、规模的量级、时间维度、错误的代价、可见性的要求。

**阅读重点**：Demo 常用干净、短小、预先构造的输入；生产输入更长尾，调用规模更大，任务持续时间更久，错误损失更高，而且必须能向用户和运维解释系统状态。五个差异说明“一次跑通”与“长期稳定服务”不是同一个验收目标。

**工程意义**：测试计划应从 happy path 扩展到脏输入、并发、长任务、部分故障和事后审计。验收指标也要从“最终答案像不像”扩展到成功率、恢复率、重复副作用率、成本和可解释性。

#### 1.5 从失败中学习：建立正确的 Agent 认知

**目录覆盖**：Agent 不是魔法而是工程；不确定性是常态；稳定性是设计出来的；失败是最好的老师；从第一天建立生产环境思维。

**阅读重点**：这节相当于全书的方法论立场。模型能力提升并不会自动消除状态错乱、权限越界和重复执行；相反，能力越强、工具越多，越需要清晰的工程边界。

**工程意义**：把故障记录作为长期资产，而不是项目结束后的附录。建议为每次失败保留 trace、状态快照、修复方案、回归测试和设计原则，形成“运行—失败—定位—修复—归纳”的闭环。

### 第 2 章 理解 Agent 系统

#### 2.1 什么是 Agent：从“会说话”到“会做事”

**目录覆盖**：Agent 从语言交互走向任务执行的定义变化。

**阅读重点**：区分聊天模型与任务型 Agent。关键不只是一次回答，而是能围绕目标感知环境、选择动作、观察结果并继续行动；同时要明确任务目标、可用工具和停止条件。

**工程意义**：系统设计应先写清任务契约，而不是先堆工具。契约至少包括输入、预期结果、允许动作、禁止动作、预算、完成判据和失败出口。

#### 2.2 最小闭环：Perception → Reasoning → Action → Observation

**目录覆盖**：感知、推理、行动、观察构成的最小循环。

**阅读重点**：闭环每一拍都可能出错：感知可能遗漏，推理可能错误，行动可能部分成功，观察可能失真。模型的“下一步”依赖观察质量，因此眼睛和手不能把内部信息混进模型可见上下文。

**工程意义**：每一拍都应留下结构化记录：模型看到什么、选择什么、工具做了什么、环境实际发生了什么。这样既能调试，也能判断失败究竟来自感知、决策还是执行。

#### 2.3 控制流与数据流：Agent 架构的两个维度

**目录覆盖**：从控制流与数据流两个维度理解 Agent 架构。

**阅读重点**：控制流决定下一步由谁执行、何时重试、何时停止；数据流决定上下文、工具参数、状态和结果如何流转。两者可能独立设计，不能因为数据能传过去，就默认控制逻辑正确。

**工程意义**：架构图应同时画出状态迁移和信息边界。尤其要标出哪些数据允许进入模型上下文，哪些只属于裁判、公证器或内部证据，防止调试信息和答案泄漏互相污染。

#### 2.4 单 Agent 系统与多 Agent 系统的本质区别

**目录覆盖**：单 Agent 与多 Agent 系统的本质差异。

**阅读重点**：多 Agent 不只是把 Prompt 拆给多个角色。它增加了通信、共识、冲突、重复工作和级联失败；角色边界可能提升专业性，也可能放大协调成本。

**工程意义**：先证明单 Agent 加明确工具无法满足需求，再引入多 Agent。多 Agent 系统需要定义消息协议、任务归属、投票或裁决规则、最大轮次，以及某个角色失联时如何继续。

#### 2.5 Agent 的分层架构

**目录覆盖**：Agent 的分层架构。

**阅读重点**：阅读时关注模型、运行时、工具、状态、记忆、策略与评估各自放在哪一层。分层的目标是隔离变化和集中约束，而不是单纯增加模块数量。

**工程意义**：模型可以替换，工具可以扩展，但状态机、权限门、预算和证据记录应有稳定接口。清晰分层能让同一套量具服务 CLI、MCP 和不同宿主，而把“决策”留给真正的大脑。

#### 2.6 统一看待主流框架的架构位置

**目录覆盖**：将主流框架放回统一架构坐标中比较。

**阅读重点**：比较框架时不要停留在 API 风格或 star 数，而应看它主要解决编排、状态、工具、记忆、部署还是评估中的哪一段，以及哪些责任仍留给开发者。

**工程意义**：选型表应记录框架提供的保证和缺失的保证。特别是恢复语义、并发模型、可观测性和安全边界，需要在实际版本与部署方式下验证，不能只照搬概念文档。

#### 2.7 Agent 不是 Prompt：为什么必须有运行时

**目录覆盖**：Agent 需要独立运行时，而不只是 Prompt。

**阅读重点**：Prompt 只能表达意图，无法可靠保证持久化、互斥、超时、取消、限流和审计。运行时把这些横切责任从模型自由裁量中拿出来，变成确定性代码。

**工程意义**：MCP server 是量具运行时的一种交付形态：它接收宿主大脑的动作意图，负责校验、执行、保存状态和返回观察，而不是偷偷启动第二个模型。这个边界也便于权限隔离和证据复核。

### 第 3 章 让 Agent 动起来：执行编排的全景图

#### 3.1 从 Demo 到生产的死亡之谷

**目录覆盖**：执行编排如何跨越 Demo 与生产之间的鸿沟。

**阅读重点**：重点寻找 Demo 默认成立、生产却不成立的假设，例如工具永远可用、任务一定可分解、上下文永远装得下、一次执行就能成功。

**工程意义**：生产编排需要把这些假设显式化，并为每个假设配置监控、预算、重试上限和降级出口。跨越“死亡之谷”靠的是失败路径设计，不只是更复杂的成功路径。

#### 3.2 拆解的艺术：从模糊意图到可执行单元

**目录覆盖**：三种分解范式、分解粒度的权衡、Plan-and-Execute 与 ReAct。

**阅读重点**：分解太粗会导致单步难以验证，太细会增加通信成本和状态依赖。Plan-and-Execute 强调先规划后执行，ReAct 强调根据观察滚动决策；二者都可能遇到计划过时或局部最优。

**工程意义**：任务单元应具有可检查的输入、输出和完成条件。规划可以随环境变化，但每个副作用仍需明确授权与幂等边界，不能把“重新规划”当作重复执行的理由。

#### 3.3 执行拓扑：串联、并联与有向无环图

**目录覆盖**：Anthropic 五种工作流模式、LangGraph 超越 DAG 的执行语义、AutoGen 四种编排模式、DAG 的工程优势、九大框架执行模型能力矩阵。

**阅读重点**：串联简单可解释，并联提高吞吐但增加资源竞争，DAG 能表达依赖却需要处理分支与汇合。目录提到部分框架超越静态 DAG，提示读者关注循环、状态和动态分支，而不是只看一张静态图。

**工程意义**：选拓扑时先看依赖是否真实存在，再考虑并发收益。动态图应受最大节点数、最大边数和全局预算约束，否则“灵活编排”可能变成无界扩张。

#### 3.4 调度的权衡：优先级、依赖与资源博弈

**目录覆盖**：依赖感知调度、动态优先级、资源约束、级联路由与便宜模型。

**阅读重点**：优先级不能脱离依赖，资源优化也不能牺牲任务正确性。级联路由可以让简单任务走低成本模型，但必须处理升级、回退和质量反馈。

**工程意义**：调度器应显式记录排队原因、资源等待、模型档位和升级条件。花更少钱的方案只有在延迟、质量与失败率可接受时才算优化。

#### 3.5 重试的陷阱：那些看起来简单却致命的代码

**目录覆盖**：基本重试模式、五个致命陷阱、自我纠正的局限、ReliabilityBench 的发现。

**阅读重点**：重试不是越多越好。需要区分暂时性错误、永久性错误和结果未知的副作用错误；还要检查退避、超时、幂等键以及重试是否真的改变了失败条件。关于 ReliabilityBench，应阅读正文确认研究设置和结论，不能仅凭标题推断。

**工程意义**：重试策略必须事先分类，并设置总时限。对于“请求超时但服务端可能已执行”的动作，自动重试尤其危险，应转入结果核验或人工处理。

#### 3.6 优雅降级：系统断裂时的最后防线

**目录覆盖**：多提供商故障转移链、四层降级策略、成本感知自动降级、熔断器。

**阅读重点**：降级是主动提供较低但明确的服务水平，不是悄悄返回半成品。切换提供商时还要考虑数据一致性、接口差异和输出兼容。

**工程意义**：降级结果应标记级别和限制，让用户知道当前是完整结果、部分结果还是缓存结果。所有降级路径都需要测试，否则它们只会在真正故障时第一次运行。

#### 3.7 熔断与限流：为失控的系统拉下电闸

**目录覆盖**：微观到宏观的限流、分层限流、雷群效应与抖动、批处理与 Prompt 压缩。

**阅读重点**：限流保护的不只是下游，也包括自身成本和任务队列。多个实例同时恢复可能形成雷群效应，因此重开熔断需要渐进策略和随机抖动。

**工程意义**：限流应覆盖用户、任务、租户、模型提供商和工具多个层级；批处理和压缩不能绕过权限或丢失关键上下文，并应记录压缩前后差异。

#### 3.8 动态调度：当计划遇上现实

**目录覆盖**：静态与动态调度的挑战、运行时重规划、COPPER 共享反思器、“智能体越多死得越快”、Mission Keeper、自带重规划能力的调度器框架。

**阅读重点**：动态重规划解决计划失效，却可能引入目标漂移和额外开销。共享反思器试图复用反思结果，Mission Keeper 关注保持原始使命；阅读时应比较它们如何避免重复反思和局部修补。

**工程意义**：每次重规划都应引用当前目标和已完成副作用，并限制重规划次数。系统需要区分“策略改变”与“任务目标改变”，后者通常需要重新授权。

#### 3.9 驯服不确定性：在概率的世界里建造确定性

**目录覆盖**：非确定性的本质、temperature 实践、结构化输出、五层输出解析恢复流水线、信心度路由、人在回路、多 Agent 投票。

**阅读重点**：temperature 不能创造确定性，结构化约束也只能提高可解析性。五层恢复流水线的价值在于逐层处理格式问题，而不是掩盖语义错误；信心度和投票也必须防止“多数错误”。

**工程意义**：解析失败应保留原文与错误，进入可观测事件。高风险或低信心动作应交给人或独立规则裁决，不能因为多个 Agent 意见一致就跳过权限与验证。

### 第 4 章 让任务跑到底：执行可靠性的工程实践

#### 4.1 Agent 失败：是编排而不是模型问题

**目录覆盖**：从编排到稳定性的进阶之路、五层 Agent 可靠性体系。

**阅读重点**：这里并非否认模型错误，而是强调系统如何承受模型错误。五层体系提示可靠性要从架构、执行、状态、恢复和评估整体设计，不能靠单点重试补救。

**工程意义**：可靠性验收应覆盖完整链路，并给每一层定义负责人和指标。模型质量、编排正确性、状态一致性和证据可信度需要分别度量。

#### 4.2 错误的第一性原理：并非所有错误都值得处理

**目录覆盖**：15 种 Agent 故障图谱、可恢复与不可恢复错误、错误的概率性本质、分层错误处理框架。

**阅读重点**：处理错误有成本，首先要判断是否可恢复、是否值得恢复、恢复是否会造成第二次损失。概率性错误意味着相同输入不保证相同结果，因此分类不能只依赖异常类型。

**工程意义**：建立错误矩阵：现象、根因层级、是否可重试、是否有副作用、可接受恢复时间、最终出口。不可恢复错误应及时停止并保留证据，而不是无限消耗预算。

#### 4.3 时间的边界：超时、中断与优雅恢复

**目录覆盖**：LLM 调用时间成本、三种超时策略、取消令牌与中断传播、可中断 Agent、心跳与续约、Kubernetes 生命周期。

**阅读重点**：超时时间需要覆盖连接、排队、推理和输出等不同阶段；取消信号必须沿调用链传播，心跳则用于区分任务仍活跃与执行者失联。

**工程意义**：执行器要能在检查点安全停止，并处理“动作可能已执行”的中断状态。容器被驱逐或节点失联时，不能仅凭新进程启动就认定旧动作没有发生。

#### 4.4 不朽的状态：如何让任务从断点重生

**目录覆盖**：LangGraph 检查点、检查点设计权衡、生产实践、Eunomia、基于检查点的断点续跑框架。

**阅读重点**：检查点不是简单保存聊天历史。它需要保存任务位置、待处理请求、执行意图、版本和重建所需状态；同时要权衡存储成本、恢复精度与一致性校验。

**工程意义**：恢复时不仅核对最终结果，还应验证初始状态和每个动作后的状态哈希。若无法证明崩溃窗口中的动作是否执行，应 fail-closed，而不是猜测后重放。

#### 4.5 幂等性悖论：AI Agent 精确、一次性执行

**目录覆盖**：Agent 幂等性的难点、“准幂等”策略、分层幂等实现。

**阅读重点**：模型不能天然保证同一动作只执行一次，网络超时也让“没收到响应”不等于“没执行”。准幂等是通过稳定标识、状态查询或去重降低重复风险，而不是声称实现数学意义上的严格幂等。

**工程意义**：副作用接口应支持幂等键和结果查询；无法去重的动作要有执行前意图记录、执行后确认和异常隔离。恢复机制与幂等机制需要一起设计。

#### 4.6 撤回的艺术：当 Agent 犯下无法撤销的错误

**目录覆盖**：补偿事务迁移、Saga、事务性沙箱、撤销挑战、可补偿操作四原则、Saga 框架与执行流程。

**阅读重点**：有些动作不能真正回滚，例如消息已发出或物理设备已移动，只能补偿。补偿本身也可能失败，因此 Saga 需要明确正向步骤、对应补偿、重试和最终人工出口。

**工程意义**：设计工具时优先选择可逆操作和沙箱。对不可逆动作提前记录足够信息，以便事后补偿，并避免补偿动作再次触发同一业务流程。

#### 4.7 马拉松选手：长时任务的生命周期工程

**目录覆盖**：有状态工作空间、上下文窗口管理、token 预算、生命周期阶段、心跳续约与关停、经验反思学习。

**阅读重点**：长任务不是短对话的简单延长。工作空间可能跨多次模型调用，上下文需要压缩与检索，经验学习也必须防止把一次偶然成功固化成错误规则。

**工程意义**：将任务划分为启动、执行、等待、恢复、完成和关停等显式状态；为每个阶段设置预算、超时与持久化要求。经验沉淀应经过验证，不能直接变成无监督的长期记忆。

#### 4.8 健康仪表盘：如何知道你的 Agent 是否真的可靠

**目录覆盖**：可观测性工具对比、SLI/SLO 建议、可靠性层级金字塔、Agent 健康度检查框架。

**阅读重点**：健康不等于进程还在，而应看任务成功率、恢复成功率、延迟、预算消耗、证据一致性和安全事件。不同可靠性层级需要不同指标。

**工程意义**：仪表盘应能从业务结果下钻到 trace 和单个动作，并将“未知”单独显示。把中断或证据不完整的任务混入成功率的做法，会制造虚假的健康。

### 第 5 章 调试与排查实战

#### 5.1 Agent 调试的特殊性

**目录覆盖**：非确定性、长时序调用链、级联错误、静默失败、多 Agent 非线性复杂度、记忆污染、主流框架调试实践差异。

**阅读重点**：传统程序的相同输入通常更容易复现，Agent 却同时受模型采样、环境变化和记忆影响。记忆污染会让历史错误持续影响后续决策，表面症状与根因可能相隔很远。

**工程意义**：调试工具应固定 seed、输入、模型版本和状态快照，同时保留真实运行中的随机性信息。排查时先确认证据可信，再讨论模型为什么这样回答。

#### 5.2 可观测性设计三要素

**目录覆盖**：传统可观测性失灵、Trace／Metrics／Logs、GenAI 事件、关键维度、OpenTelemetry 语义约定、框架生态实践。

**阅读重点**：Trace 重建决策故事，Metrics 量化整体行为，Logs 提供细节，GenAI 事件补充 Prompt、模型输出和工具语义。四类信号互补，不能相互替代。

**工程意义**：统一 run、step、session 和 tool-call 标识，才能跨信号关联。观测字段还应兼顾隐私与权限，不能为了调试把密钥或敏感用户内容无差别写入日志。

#### 5.3 日志追踪：还原 Agent 决策过程

**目录覆盖**：Run 与 Thread、token 级追踪、决策路径可视化、会话回放、记忆操作日志、Span 级评估、时间旅行调试、InnerTrace 事件溯源。

**阅读重点**：追踪的目标不是收集更多文本，而是还原“当时看见了什么、依据什么、做了什么、得到什么”。时间旅行调试允许从检查点分叉，但必须标明哪条是原始运行、哪条是实验分支。

**工程意义**：事件溯源记录应追加而非随意覆盖，并与状态版本关联。回放既可用于学习，也可生成测试，但模型输出变化时不能机械期待逐字相同。

#### 5.4 故障诊断方法论

**目录覆盖**：三个框架的故障分类对比、分层根因分析、约束与隔离、LLM-as-a-Judge、红队、修复验证闭环、Session／Trace／Span 三级评估、trace-to-test Harness。

**阅读重点**：诊断应先分层定位，再决定是否用模型辅助标注。LLM-as-a-Judge 能扩展评估，却可能引入偏差，因此高风险结论需要规则或独立证据交叉验证。

**工程意义**：把真实 trace 转成回归用例，并同时保留正向与反向对照。修复后不仅重跑失败样本，还要确认没有破坏原本正常的路径。

#### 5.5 常见故障排查手册

**目录覆盖**：幻觉级联、工具调用失败、上下文溢出、无限循环、多 Agent 通信故障、Prompt 注入、记忆系统故障、供应链安全与权限逃逸、速查表、调试就绪度评估。

**阅读重点**：这节适合作为案头索引。每类故障都应先收集最小证据，再按可能根因排序，最后给出安全止损动作；不要一开始就盲目重写 Prompt。

**工程意义**：排查手册应包含现象、检查项、证据位置、临时缓解、根治方法和回归测试。涉及权限逃逸时，第一步是隔离和撤销能力，而不是继续观察攻击者行为。

### 第 6 章 生产级部署

#### 6.1 性能优化的关键指标

**目录覆盖**：Demo 到生产的性能鸿沟、推理延迟三层度量、吞吐与并发、稳定运行时间、框架性能架构对比。

**阅读重点**：端到端延迟不等于模型推理延迟，还包括排队、工具调用、重试和编排开销。吞吐提升可能以更高成本或更低成功率换取。

**工程意义**：建立分位数延迟、任务成功率、并发上限、单位成功任务成本和最长稳定运行时间等指标，再根据瓶颈选择模型、架构或引擎优化。

#### 6.2 成本控制：让 Agent 用得起

**目录覆盖**：token 经济、模型层优化、架构层优化、推理引擎优化、运营层成本治理。

**阅读重点**：成本优化应优先减少无效工作，例如重复上下文、无界重试和过度反思，而不只是换便宜模型。架构层往往比单次调用单价更能决定总账单。

**工程意义**：按任务核算预算，并把预算消耗写入运行记录。预算耗尽时要明确降级或停止，防止系统为了“完成”而突破费用边界。

#### 6.3 安全边界与防护

**目录覆盖**：攻击面全景、Production Harness、七层纵深防护、约束性部署、框架安全比较、持续安全。

**阅读重点**：Agent 会读取不可信内容并调用真实工具，因此提示注入、数据外泄、越权操作和供应链风险相互交织。安全不能只依赖模型识别恶意指令。

**工程意义**：把权限、参数校验、网络隔离、工具白名单和高危动作审批放进运行时。Prompt 可以辅助识别，但不能作为唯一安全边界。

#### 6.4 合规性考量

**目录覆盖**：全球合规图谱、数据治理与隐私、透明度与可解释性、Compliance-as-Code 2.0。

**阅读重点**：合规要求随地区、行业和数据流向变化。可解释性也不只是展示思维链，而是能够说明系统使用了哪些数据、规则和工具，以及谁批准了关键动作。

**工程意义**：把数据保留、删除、访问和审计要求转成可测试策略。具体法律结论需要结合业务所在地和专业意见，不能仅凭框架功能列表判断合规。

#### 6.5 从部署到运维的闭环

**目录覆盖**：五种部署架构、五层监控、日志追踪与幽灵调试、智能告警、持续部署与灰度发布、从失败中学习。

**阅读重点**：部署不是终点。灰度发布需要可比较的基线、快速回退和真实任务指标；告警则应指向可执行动作，避免只通知“模型又报错了”。

**工程意义**：将运行证据接入发布流程，新版本先在有限流量下验证质量、成本和安全，再逐步扩大。回退时还要处理已经产生的副作用和持久化状态。

### 第 7 章 审片官的诞生——VLM 闭环视频生产 Agent

#### 7.1 线性管道的终结

**目录覆盖**：Prompt Drift、VLM-as-a-Judge、从生成后检查到生成中感知。

**阅读重点**：线性生成管道容易在末端才发现整体偏离需求。VLM 作为审片官可以把视觉反馈提前接入，但评估标准必须稳定，否则同一画面可能因评审波动而反复修改。

**工程意义**：把生成、评审和修订组成有预算的闭环。评审信号应结构化，并区分必须修复与可接受差异，避免无限“精修”。

#### 7.2 自反思循环——Agent 如何“知错能改”

**目录覆盖**：反思的力量、视频生成中的应用、状态保持。

**阅读重点**：反思有效的前提是反馈具体且可执行。状态保持记录已经尝试过什么、为什么失败，避免模型在相同坑里循环。

**工程意义**：维护修订历史、失败原因和已排除方案。每轮反思也要计入延迟与成本，并设置停止条件；如果新结果没有客观改善，应结束循环或转人工。

#### 7.3 延伸思考——反思的边界在哪里

**目录覆盖**：反思悖论、从审片扩展到更多场景。

**阅读重点**：更多反思可能带来过度编辑、目标漂移和成本膨胀。需要判断反思是否提供了新证据，而不只是换一种说法重复原意见。

**工程意义**：设置最大反思轮次、收益阈值和独立验收。对于不可逆或高成本场景，宁可保留原始版本，也不让自反思无界修改。

### 第 8 章 泥土与代码之间——农业机器人的决策图谱

#### 8.1 当 AI 走进田间地头

**目录覆盖**：精准农业 Agent、识别到决策的置信度分流、状态机。

**阅读重点**：识别准确不等于操作决策正确。低置信度应进入复核、人工或保守动作，而不是强行分类；状态机则限制危险操作的前后条件。

**工程意义**：把感知置信度、设备状态和安全条件共同作为动作闸门。纯软件 Agent 的“再试一次”，在物理环境中可能意味着不可逆的作物或设备损失。

#### 8.2 人机协同——在危险面前踩下刹车

**目录覆盖**：完全自主的风险、中断机制设计、信任构建。

**阅读重点**：人工介入必须及时、可达且信息充分。暂停按钮存在并不等于系统能安全停止，还要考虑惯性、延迟和当前动作状态。

**工程意义**：为关键操作设置独立急停、明确的责任边界和可理解的系统状态。恢复运行前需要重新确认环境，不能简单从中断点继续。

#### 8.3 优雅降级——当传感器离线时

**目录覆盖**：现实世界不可靠性、降级策略、CrewAI 的角色哲学。

**阅读重点**：传感器离线时，系统应知道自己“不知道”哪些信息。降级可能是减速、保守路径、人工接管或安全停止，而不是假装数据仍然可信。

**工程意义**：为每种传感器定义质量指标和失效策略，并将降级状态暴露给操作者。角色分工可以辅助决策，但不能替代硬件安全联锁。

#### 8.4 实战——AgriClaw 的完整架构

**目录覆盖**：架构全景、关键节点实现、一次完整植保任务的端到端示例。

**阅读重点**：沿真实任务追踪感知、规划、审批、执行、监测和恢复，重点检查异常分支是否进入架构图，而不只是主流程是否完整。

**工程意义**：案例可作为物理 Agent 的需求模板：每个节点标注输入可信度、允许动作、停止条件、人工接口和审计证据。

### 第 9 章 裸机上的进化论——自治环境演进与代码修复 Agent

#### 9.1 ACI——Agent 与计算机的界面革命

**目录覆盖**：CLI 到 ACI、SWE-agent、Claude Code 工具哲学、OpenHands 沙箱。

**阅读重点**：Agent 使用计算机的接口决定了它的能力上限和错误率。ACI 不只是命令集合，还包括错误反馈、输出格式、状态查询和安全边界。

**工程意义**：为 Agent 设计专用工具时，应让成功、失败、部分完成和结果未知都可辨识。读写命令、测试命令和高危部署命令应分级授权，并优先在沙箱内执行。

#### 9.2 多 Agent 博弈——当部署者遇上监控者

**目录覆盖**：对抗式架构、OOM 协同诊断、共识机制。

**阅读重点**：部署者与监控者的分歧可以提供交叉验证，但也可能互相阻塞。共识机制需要明确谁裁决、需要多少证据、意见冲突时怎么办。

**工程意义**：诊断 Agent 与修复 Agent 的权限应分离，生产变更必须通过独立闸门。对于 OOM 等复杂故障，应先收集指标和堆栈证据，再让多个角色提出和检验假设。

#### 9.3 动态扩展——Agent 的自我进化

**目录覆盖**：量化与自主降维、AutoResearch、从代码修改到环境重建。

**阅读重点**：自我进化涉及系统修改自身策略、代码甚至环境，风险高于普通任务自动化。“能运行实验”不等于“可以把实验结论直接部署”。

**工程意义**：实验与生产必须隔离，候选改动需要可回滚和独立评估。自动研究产生的结论应标注证据范围，避免把一次成功扩展成普遍规律。

#### 9.4 实战——CyberOps 的完整架构

**目录覆盖**：架构全景、关键节点、从仓库到生产的端到端示例。

**阅读重点**：重点关注代码修改如何经过测试、审查、部署和监控，以及监控结果如何回流。案例的价值不仅在自动修复，还在整条变更链的责任边界。

**工程意义**：可复用为 Coding Agent 的生产流水线模板：仓库读取、沙箱修改、确定性测试、人工或规则审批、灰度部署、运行监控、失败回退。

### 第 10 章 框架丛林与 Agent 的未来

#### 10.1 十大框架横评

**目录覆盖**：对十大框架进行横向比较。

**阅读重点**：官方目录没有在标题中列出全部框架名称，因此不应凭空补全名单。阅读正文时重点记录比较维度、版本时间和适用场景，并检查作者是否给出可复现实验。

**工程意义**：选型不应只复制横评排名。用自己的任务做小规模验证，至少覆盖恢复、并发、工具错误、长上下文、成本和部署隔离。

#### 10.2 三条设计哲学

**目录覆盖**：简单胜于复杂、状态机优于无限循环、接口即性能。

**阅读重点**：三条哲学分别约束架构复杂度、控制方式和交互质量。状态机不是禁止动态行为，而是要求动态行为发生在明确状态与转换规则中。

**工程意义**：优先删除不必要的抽象，把任务状态显式化，并把工具接口设计当作性能工程的一部分。稳定、信息完整的接口往往比更大的模型更能提升整体可靠性。

#### 10.3 Agent 的下一步

**目录覆盖**：A2A 协议、从工具调用到环境交互、持续学习、辅助到自治的伦理边界。

**阅读重点**：Agent 间通信标准化、环境操作和持续学习会扩大能力，也会扩大攻击面与责任范围。自治程度必须与授权、可解释性和可撤销性匹配。

**工程意义**：采用 A2A 等协议时仍需处理身份、权限、消息可信度和任务状态。持续学习应经过评估与审批，不能让系统在没有监督的情况下自行改变生产行为。

#### 10.4 写给读者的行动建议

**目录覆盖**：面向读者的后续行动建议。

**阅读重点**：将全书方法落到一个真实小项目：先定义失败模式，再实现最小闭环，随后补状态、恢复、观测和安全边界。不要试图一次引入全部框架。

**工程意义**：建议从现有系统选择一条高风险链路，建立故障台账和回放用例，逐项验证。每轮只解决一类可复现问题，并用测试和文档固定成果。

## 6. 十章深挖：从问题、机制到验收

本节不是目录的简单扩写，而是把官方目录中的主题串成可执行的工程框架。以下故障表、状态机、指标公式、JSON 示例和验收实验均为**整理者给出的参考实现**，不是书中原文，也不声称与作者的具体方案完全一致。

### 第 1 章深挖：先建立故障语言，再谈 Agent 能力

#### 6.1.1 六种崩溃模式应当分开度量

| 故障模式 | 最早可观测信号 | 常见误判 | 应设置的硬边界 |
| --- | --- | --- | --- |
| 无限循环 | 重复动作、重复观察、状态长期无进展 | 认为模型“还没想明白” | 最大步数、无进展检测、总墙钟时间 |
| 上下文溢出 | 输入 token 接近预算、旧信息被截断 | 只换更大窗口 | 上下文预算、分层保留、压缩留痕 |
| 输出格式失控 | JSON 解析失败、字段缺失、工具参数非法 | 全部归因于 Prompt 不好 | Schema 校验、有限修复、失败留痕 |
| 资源耗尽 | 队列增长、并发打满、磁盘或费用异常 | 只增加机器 | 并发上限、队列上限、磁盘与费用闸门 |
| 级联失败 | 下游超时上升、重试流量放大 | 各服务分别重启 | 熔断、隔离、退避与负载削减 |
| 静默失败 | 进程健康但业务结果长期不变 | 看心跳判断任务成功 | 独立完成判据、进展信号、结果对账 |

关键不是记住六个名词，而是让每类故障都有**信号、阈值、处置和证据**。如果某类故障只能靠人翻聊天记录发现，它实际上还没有被工程化。

#### 6.1.2 一个失败案例应还原成八段证据

建议按以下顺序复盘：原始目标、环境初态、模型可见上下文、模型动作、工具请求、工具实际结果、状态变化、最终业务结果。每一步都记录时间、run/step 标识和错误类别。

复盘时最常见的问题是把“模型选错了工具”当作根因，却没有检查模型当时是否看到了正确工具说明、工具是否把失败包装成成功文本、状态是否已经被前一步污染。根因可能位于决策层，也可能位于接口层或恢复层。

#### 6.1.3 Demo 验收与生产验收不是一张表

Demo 可以只检查 happy path；生产至少还应检查：脏输入、重复请求、并发请求、工具超时、进程崩溃、磁盘写满、预算耗尽、恶意输入、长尾延迟和证据不完整。每一项都应有明确预期，而不是统一写“系统应保持稳定”。

**本章最小验收实验**：故意让一个工具返回非法格式，确认系统不会无限重试；让另一个工具“执行成功后断开连接”，确认系统进入结果未知状态而不是重复执行；让进程在状态写入前后分别崩溃，确认两种崩溃窗口都不会被误报为成功。

### 第 2 章深挖：画清架构图，也画清信息边界

#### 6.2.1 一个可落地的五层参考架构

| 层 | 主要责任 | 不应承担的职责 |
| --- | --- | --- |
| 模型层 | 理解目标、提出动作、解释观察 | 持久化、互斥、权限最终裁决 |
| 运行时层 | 状态机、调度、预算、重试、取消 | 代替模型做业务判断 |
| 工具层 | 参数校验、执行、结果查询、幂等控制 | 隐藏失败或伪造环境反馈 |
| 状态层 | 检查点、事件、工作空间、恢复 | 无边界保存敏感数据 |
| 评估层 | 独立验收、回放、偏差检测、证据认证 | 向决策模型泄漏答案 |

“大脑归宿主、判据归量具”就是这种分层的一种具体形态：模型只提出动作，量具决定动作是否合法、执行是否可信、结果是否可公开。

#### 6.2.2 控制流与数据流要用两套图检查

控制流图至少标出开始、等待模型、校验、执行、观察、完成、失败、中断和恢复。数据流图标出用户输入、环境观察、工具结果、内部状态、模型上下文和最终输出。

特别检查三类交叉：内部裁判信息是否进入模型上下文；模型可见观察是否混入未发生的预测；工具输出是否包含不应展示给用户的敏感字段。很多“模型幻觉”实际是数据边界没画清。

#### 6.2.3 单 Agent 与多 Agent 的取舍可以量化

多 Agent 的收益来自分工和视角多样性，成本来自通信、同步、重复上下文与裁决。若任务只有一个明确的串行决策链，多 Agent 往往只会增加失败点。

引入多 Agent 前先回答：角色是否掌握不同信息？是否必须独立验证？冲突由谁裁决？最大通信轮数是多少？某个角色无响应时任务如何结束？如果这些问题没有答案，角色 Prompt 写得再漂亮也只是装饰。

**本章最小验收实验**：删掉一个非必要角色，比较成功率、成本和延迟；再故意让一个角色返回错误结论，检查裁决机制是否能识别并隔离，而不是让错误意见自动成为多数票。

### 第 3 章深挖：编排的核心是限制搜索空间

#### 6.3.1 工作流模式按任务结构选择

| 模式 | 适合的任务 | 主要风险 | 必要约束 |
| --- | --- | --- | --- |
| 串行 | 强依赖、顺序明确 | 单点失败阻塞全程 | 每步验收与恢复点 |
| 并联 | 相互独立的子任务 | 资源争抢、结果合并困难 | 并发上限与汇合规则 |
| DAG | 依赖关系可预先表达 | 静态计划失效 | 分支上限、失败传播 |
| ReAct | 需要根据观察滚动决策 | 局部循环、目标漂移 | 步数、进展与停止条件 |
| Plan-and-Execute | 目标可先规划再执行 | 计划过时、过度拆解 | 重规划门槛与预算 |

模式可以组合，但组合后必须重新计算最坏调用量，不能把每个子图的局部上限当作全局上限。

#### 6.3.2 重试前先过一张错误分类表

| 错误类型 | 示例 | 能否自动重试 | 处置 |
| --- | --- | --- | --- |
| 暂时性且无副作用 | 连接建立失败 | 可以，有限退避 | 复用幂等请求 |
| 永久性参数错误 | 字段不合法 | 不可以 | 修复参数或终止 |
| 结果未知且可能有副作用 | 支付请求超时 | 不可直接重试 | 查询结果或人工核验 |
| 模型输出格式错误 | JSON 不完整 | 有限修复 | 保留原文、约束重生成 |
| 业务规则拒绝 | 权限不足 | 不可以 | 停止并记录原因 |

一个简单但关键的上界是：若每个逻辑动作最多重试 `R` 次，每个任务最多有 `N` 个动作，则调用量上界应约为 `N × R`，再计入并行分支和压缩、评估等辅助调用。没有这个总账，局部“重试三次”也可能把系统拖垮。

#### 6.3.3 结构化输出需要分层，而不是只写“请返回 JSON”

整理者建议采用五层参考流水线：提取候选输出、剥离干扰格式、按 Schema 解析、执行有限修复、进入语义与权限校验。前三层解决“能不能读”，后两层解决“读出来以后能不能用”。

每次失败都应记录原始输出、错误位置和修复动作。若修复后仍失败，应交由人工或降级路径，不能把格式修复变成新的无限循环。

#### 6.3.4 动态重规划必须带着已完成副作用

重规划不是清空历史重新开始。新计划至少要知道：目标是否变化、哪些动作已经完成、哪些结果仍有效、哪些副作用不可撤销、剩余预算是多少。

建议设置重规划门槛：环境发生实质变化、关键假设被证伪、依赖失败导致原计划不可执行。仅因为模型“想换一种做法”不应触发重规划，否则容易演变成反复折腾。

**本章最小验收实验**：让一个并行分支持续失败，检查系统是否削减负载而不是增加重试；让环境在中途改变，检查新计划是否保留已完成的幂等操作；让模型连续输出非法结构，检查修复次数是否有上限。

### 第 4 章深挖：可靠性的核心是处理“未知”

#### 6.4.1 状态机先于恢复代码

推荐的任务状态至少包括：已创建、等待决策、动作意图已保存、动作执行中、等待观察、已完成、可恢复失败、不可恢复失败、结果未知／中断。状态可以按系统调整，但“执行中”和“结果未知”不能省略。

每次转换都应有前置条件、后置条件和持久化要求。尤其要禁止从“结果未知”直接跳回“等待决策”，那等于默认动作没有发生。

#### 6.4.2 副作用前的执行意图能封住崩溃窗口

一个危险的时序是：动作已经发出，进程在保存结果前崩溃。恢复者无法知道服务端是否执行，自动重放可能造成两次扣款、两封邮件或两次部署。

更安全的时序是：先原子保存动作意图与请求标识，再执行动作，最后保存结果。恢复时若意图存在但结果不存在，任务应进入“结果未知／中断”，通过外部幂等键、结果查询或人工核验处理，而不是直接重放。

#### 6.4.3 幂等能力应按动作分级

| 动作 | 推荐策略 |
| --- | --- |
| 只读查询 | 可有限重试，仍需限制总量 |
| 创建资源 | 使用客户端幂等键，返回同一资源 |
| 发送通知 | 使用消息 ID 去重，提供送达状态查询 |
| 资金或库存变更 | 业务幂等键、事务记录、结果核验 |
| 物理或不可逆操作 | 执行前确认、安全联锁、事后补偿 |

“准幂等”必须写明假设，例如依赖服务端在多大时间范围内保存幂等记录。超过保留期后是否仍能去重，不能默认成立。

#### 6.4.4 Saga 补偿不是Ctrl+Z

Saga 把长事务拆成多个可局部完成的步骤，每一步都有对应补偿。补偿可能失败，也可能只能减轻损失，因此需要独立的补偿状态、重试上限和人工出口。

设计可补偿操作时问四个问题：是否可重复执行？是否保留足够撤销信息？补偿是否会产生新副作用？补偿失败后谁负责？不能回答的问题应尽量在沙箱或人工审批阶段解决。

#### 6.4.5 可靠性指标必须把“未知”单独留下

建议至少跟踪任务成功率、独立验收通过率、可恢复失败恢复率、重复副作用次数、结果未知任务数、恢复后状态一致率和中断任务证据完整率。

分母也要明确：中断任务不能因为最终没有完成就从成功率分母中消失；否则系统会通过提前终止或丢弃困难任务“提升”成功率。

**本章最小验收实验**：在动作执行前、执行中、结果保存前三个位置注入崩溃，逐窗检查是否重复副作用；篡改初始状态和中间状态，确认恢复不是只比较末态；让补偿动作失败，确认任务进入明确的人工处理状态。

### 第 5 章深挖：可观测性要能回答因果问题

#### 6.5.1 一条最小 Agent 事件应该包含什么

下面是一份整理者建议的事件结构，字段可按业务调整：

```json
{
  "run_id": "run-123",
  "step": 7,
  "event_type": "tool_result",
  "parent_span_id": "span-456",
  "timestamp": "2026-11-24T08:00:00Z",
  "tool": "update_record",
  "request_id": "req-789",
  "outcome": "unknown",
  "error_category": "timeout_after_dispatch",
  "state_hash": "example-state-hash",
  "evidence_ref": "events.jsonl#L42"
}
```

重点不是字段越多越好，而是能否串联输入、决策、动作和状态。敏感内容应脱敏或受权限控制，不能为了调试扩大数据暴露面。

#### 6.5.2 Trace、Metrics、Logs 与 GenAI 事件各答不同问题

Trace 回答“这次任务经过哪些步骤”；Metrics 回答“总体成功率和延迟如何”；Logs 回答“某个错误具体发生了什么”；GenAI 事件补充“模型看到了什么、输出了什么、如何解析”。四者通过统一标识关联。

只看 Metrics 会丢失决策细节，只看 Trace 难以发现系统性趋势，只看 Logs 又容易被海量文本淹没。好的仪表盘应允许从异常指标下钻到具体 trace，再定位到单个事件。

#### 6.5.3 回放测试要声明复现的是哪一层

回放至少有三层：固定输入重跑、固定状态重放、逐事件确定性重放。模型采样、外部服务和当前时间都可能变化，因此不能笼统承诺“完全复现”。

测试应明确哪些部分必须逐字一致，例如状态哈希、工具调用次数和权限判决；哪些只允许语义一致，例如模型自然语言解释。把两者混在一起，会产生大量无意义失败。

#### 6.5.4 调试顺序建议固定为六步

先确认故障现象与业务影响，再检查证据是否完整，然后定位首个偏离预期的状态转换，接着区分模型、接口、环境和编排原因，最后做最小修复并生成回归测试。

LLM-as-a-Judge 可以辅助归类，但不应独自裁定资金、权限和物理安全等高风险问题。红队测试也应进入持续流程，而不是上线前一次性活动。

**本章最小验收实验**：从一条真实失败 trace 自动生成测试，确认能够复现；修复后同时重跑失败样本和正常对照；故意丢失一条关键事件，确认系统能把证据不完整与任务失败区分开。

### 第 6 章深挖：部署是持续约束，不是最后一步

#### 6.6.1 性能指标要同时覆盖速度、质量与成本

建议记录端到端延迟的 P50／P95／P99、模型推理延迟、工具延迟、排队时间、吞吐量、并发上限、任务成功率、单位成功任务成本和最长稳定运行时间。

只优化模型延迟可能无效，因为真正瓶颈可能在工具或队列；只提升吞吐也可能增加错误和费用。优化目标应写成“在质量与预算约束下降低端到端延迟”，而不是孤立追求某个数字。

#### 6.6.2 成本应按任务核算

一个实用的成本模型是：总成本等于模型输入、输出、工具、存储和失败重试成本之和，再除以**独立验收通过的任务数**。失败任务消耗也必须进入分子。

模型路由、上下文压缩、缓存和减少无效重试都可能降本，但要评估质量损失。缓存尤其要检查数据时效、租户隔离和权限，不能用错误缓存换取低成本。

#### 6.6.3 七道运行时防护门

官方目录提到“七层纵深防护”，但没有在公开标题中列出每一层名称。以下是整理者归纳的七道参考防护门，不能当作作者原表：

1. 身份与权限：谁可以发起、谁可以批准。
2. 输入边界：检测不可信内容、超长输入和注入企图。
3. 工具边界：白名单、参数校验、最小权限和沙箱。
4. 网络与数据边界：出站限制、租户隔离、敏感数据保护。
5. 执行边界：步数、时间、token、费用和并发上限。
6. 输出边界：Schema、内容检查和发布前审批。
7. 审计与响应：证据留存、异常告警、撤销和应急止损。

Prompt 可以参与识别，但不能替代其中任何一道确定性闸门。

#### 6.6.4 灰度发布必须能比较和回退

发布前冻结评估集和成功判据；先在小流量运行，比较质量、成本、延迟和安全事件；再逐步扩大。回退不仅是切回旧版本，还要考虑新版本已经写入的状态和已经触发的副作用。

告警应指向处理动作，例如“暂停新任务”“降级到只读”“撤销某工具权限”，而不是只发一句“Agent 异常”。

**本章最小验收实验**：模拟模型提供商故障、预算突增和工具越权，确认系统分别进入降级、停止和隔离状态；在灰度期间注入质量退化，确认能自动暂停扩量并保留对照证据。

### 第 7 章深挖：反思必须有反馈、记忆和停止条件

#### 6.7.1 视频生成闭环可以拆成六个状态

等待生成、初步审查、需要修订、重新生成、等待人工、接受或拒绝。每次修订绑定原版本、评审意见和修改目标，避免覆盖历史后无法比较。

VLM-as-a-Judge 的评估标准应相对稳定，例如镜头一致性、主体稳定性、文字错误和任务符合度。若评审标准随每次输出漂移，系统会陷入“越改越不满意”。

#### 6.7.2 自反思不是重复调用模型

有效反思至少包含：发现差异、提出可执行修改、记录已尝试方案、生成新结果、用同一标准复评。只是把原结果再总结一遍，不产生新证据，也不应继续消耗预算。

停止条件可以包括最大轮次、连续无改善、预算耗尽、风险升级或需要人工判断。越反思不一定越好，过度反思可能破坏原本合格的部分。

**本章最小验收实验**：让评审连续两次给出相互冲突的意见，检查系统是否转人工；让修改没有提升客观评分，检查是否停止；让系统在预算耗尽前保留最佳版本，而不是只剩最后一次失败结果。

### 第 8 章深挖：物理世界把“未知”变成安全问题

#### 6.8.1 置信度必须映射到动作，而不只是标签

| 感知状态 | 允许动作 | 禁止动作 |
| --- | --- | --- |
| 高置信且安全条件满足 | 执行已授权操作 | 越过审批边界 |
| 低置信但环境安全 | 重测、换传感器、请求人工 | 高风险自动执行 |
| 传感器冲突 | 保守降级或停止 | 选择更方便的结论 |
| 关键传感器离线 | 安全停止或受限模式 | 假装系统仍完全自主 |
| 安全联锁触发 | 立即进入停止流程 | 由模型投票解除 |

状态机的价值是把业务判断与安全联锁分开。模型可以建议路径，但不能自行解除硬件或权限保护。

#### 6.8.2 人机协同要设计响应时间与信息

人工介入界面至少显示当前动作、环境状态、风险原因、已执行步骤和可选处置。暂停和急停还要考虑设备惯性、网络延迟和通信中断。

恢复前应重新确认环境，而不是从中断状态机械继续。人机信任来自可预测行为、清晰权限和可解释的降级，而不是宣称系统“几乎不会错”。

#### 6.8.3 传感器离线要分级降级

非关键传感器离线可以重测或降低速度；关键传感器离线应进入受限模式或安全停止；多传感器冲突应触发保守策略。降级状态必须对操作者可见，并记录进入和退出条件。

**本章最小验收实验**：分别断开视觉、定位和通信模块，确认动作集合按风险收缩；在动作执行中按下急停，确认传播链路完整；恢复传感器后，确认不会自动跳过环境复核。

### 第 9 章深挖：Coding Agent 的重点是变更链可信

#### 6.9.1 ACI 的工具应让结果“可判定”

| 工具类别 | 推荐返回 |
| --- | --- |
| 读文件 | 内容、范围、编码、是否存在 |
| 搜索 | 命中、上下文、是否截断 |
| 修改文件 | diff、写入结果、版本标识 |
| 运行测试 | 退出码、摘要、完整日志引用 |
| 执行命令 | 退出码、stdout／stderr、超时状态 |
| 部署 | 部署 ID、状态、可回退版本 |

“命令已执行”不等于“业务成功”。测试通过、独立审查和部署健康应分别表达。

#### 6.9.2 部署者与监控者应分工但不互相阻塞

部署者负责提出变更，监控者负责观察影响，审批闸门负责授权，裁判负责最终验收。共识不是简单投票，而是明确证据优先级和冲突处理。

OOM 诊断应先确认内存指标、进程生命周期、日志和最近变更，再提出假设。多个 Agent 同时修改系统可能扩大故障，因此诊断与修复权限要分离。

#### 6.9.3 自我进化需要四道闸门

候选生成、沙箱实验、独立评估、审批部署。每一步都保留输入、代码差异、测试结果和评估证据。自动研究可以提高候选产生速度，但不能绕过生产变更审批。

从代码修改走向环境重建时，还要确认重建结果可复现、资源可回收、网络权限受控，避免实验系统影响真实服务。

**本章最小验收实验**：让修复 Agent 生成能通过单元测试但破坏集成的改动，确认独立验证能拦截；让两个 Agent 给出冲突诊断，检查是否进入明确裁决；让部署失败，确认能回到已知版本并保留证据。

### 第 10 章深挖：选框架、定哲学、控自治边界

#### 6.10.1 框架横评应改成自己的验证矩阵

| 维度 | 需要验证的问题 |
| --- | --- |
| 状态与恢复 | 崩溃后能恢复到什么粒度？状态是否可审计？ |
| 执行模型 | 支持哪些依赖、循环和动态分支？ |
| 工具接口 | 错误、超时和部分成功如何表达？ |
| 可观测性 | 能否导出事件并关联外部追踪？ |
| 安全 | 权限、沙箱和审批在哪里执行？ |
| 成本 | 预算与限流能否在任务级生效？ |
| 运维 | 扩缩容、灰度、回退和版本迁移怎么做？ |

横评名单和版本会变化，真正稳定的是这些验证问题。不要用功能数量代替任务实测。

#### 6.10.2 三条设计哲学可以变成设计审查

“简单胜于复杂”要求每个抽象都有明确收益；“状态机优于无限循环”要求状态和转换可列举、可验证；“接口即性能”要求工具返回结构清晰、错误可判、信息不过量。

审查时可以直接问：这个模块能否删除？系统有多少种状态？非法转换会不会被拒绝？一个工具成功、失败和结果未知能否区分？如果答不清，架构通常还没有完成。

#### 6.10.3 A2A 与持续学习扩大能力，也扩大信任问题

Agent 间通信至少需要身份认证、能力描述、任务授权、消息完整性、超时和争议处理。持续学习还要明确哪些经验可以自动更新，哪些必须经过评估和审批。

自治等级应与可逆性和影响范围匹配。只读、可撤销、业务写入、资金或物理操作，不应共享同一套授权强度。

#### 6.10.4 行动建议可以落成三轮迭代

第一轮选一个窄任务，建立最小闭环、状态与 trace；第二轮注入失败，补齐重试、恢复、幂等和独立验收；第三轮进入灰度，补齐成本、安全、监控和回退。每轮都应有可运行证据，而不是只更新架构图。

**本章最小验收实验**：用同一组任务比较两个候选框架，不比较宣传功能，而比较恢复、错误表达、成本和审计；再故意让 Agent 间消息冲突，确认授权与裁决不会被协议便利性绕过。

#### 6.10.5 跨章节故障治理总表

下表把全书主题压缩成一张工程对照表。它是整理者的综合，不是书中原表。

| 故障或风险 | 首选机制 | 必须留下的证据 | 验收方式 |
| --- | --- | --- | --- |
| 无限循环 | 最大步数、无进展检测、总时限 | 步数、停止原因、重复动作 | 注入循环后必须按时停止 |
| 上下文失控 | 分层保留、压缩、token 预算 | 压缩前后差异、截断记录 | 长任务不突破预算且关键信息可追溯 |
| 输出格式错误 | Schema、有限修复、语义校验 | 原文、解析错误、修复次数 | 非法输出不能直接进入执行器 |
| 重复副作用 | 幂等键、执行意图、结果未知状态 | 请求 ID、inFlight、结果状态 | 崩溃窗口内不重复执行 |
| 状态被篡改 | 初始与逐帧哈希、版本校验 | stateHash、revision、恢复日志 | 改动任一帧都能被发现 |
| 静默失败 | 独立完成判据、进展信号、结果对账 | 业务结果、验收结论、异常原因 | 进程健康不能冒充任务成功 |
| 级联失败 | 隔离、熔断、限流、降级 | 熔断状态、流量变化、降级级别 | 下游故障不会导致重试风暴 |
| 长任务丢失 | 生命周期、检查点、心跳续约 | 阶段转换、锁状态、恢复点 | 失联后能区分活跃与中断 |
| 成本失控 | 任务预算、路由、缓存、失败核算 | token、费用、重试、降级记录 | 预算耗尽时明确停止 |
| Prompt 注入与越权 | 最小权限、白名单、沙箱、审批 | 权限判决、工具参数、审批记录 | 恶意文本不能扩大工具权限 |
| 多 Agent 冲突 | 独立证据、裁决规则、最大轮次 | 各方意见、投票、最终裁决 | 错误多数意见不能直接执行 |
| 自反思失控 | 最大轮次、收益阈值、最佳版本保留 | 每轮评分、修改目标、停止原因 | 连续无改善时退出循环 |
| 物理环境危险 | 状态机、安全联锁、人工接管 | 传感器质量、急停、恢复确认 | 关键传感器失效时安全降级 |

#### 6.11 分阶段落地路线

**第一阶段：可运行与可解释。** 选一个窄任务，明确输入、工具、完成判据和停止条件；记录每次模型输入、动作和工具结果。验收标准是能解释一次成功和一次失败。

**第二阶段：可恢复与防重复。** 增加检查点、执行意图、幂等键、超时取消和错误分类；注入进程崩溃与网络断开。验收标准是任何动作都不会在状态未知时被自动重放。

**第三阶段：可观测与可验证。** 建立统一事件标识、指标和 trace 回放；把真实失败转成回归测试。验收标准是能复现故障、证明修复，并区分模型质量与系统质量问题。

**第四阶段：可部署与可约束。** 增加权限沙箱、预算、熔断限流、灰度、回退和审计。验收标准是故障、攻击和成本突增都有确定性出口。

这条路线的重点不是先选哪个框架，而是每一阶段都产生可运行、可检查的证据。

## 7. 按工程链路提炼的重点

### 5.1 执行编排：不要把“会循环”当作“会干活”

第 3 章涉及任务分解、执行拓扑、依赖调度和资源约束。其关注点不只是选择哪个框架，而是：

- 一个模糊任务如何被拆成可执行单元。
- 串行、并行和有向无环图分别适合什么任务。
- 计划失效后如何重新规划。
- 资源不足时如何降级，而不是无限重试。
- 面对概率性输出，如何通过结构化解析与恢复流水线提高确定性。

### 5.2 可靠性：模型不确定，但工程可以设置边界

第 4 章是全书与生产系统最直接相关的部分，涉及：

- 可恢复错误与不可恢复错误的区分。
- 超时、取消、中断和优雅恢复。
- 检查点的保存内容与设计权衡。
- 断点续跑与确定性重放。
- 幂等性、“准幂等”策略和分层实现。
- 不可逆错误的 Saga 补偿。
- 长任务的上下文、预算、心跳、续约和关停。
- SLI/SLO 与 Agent 健康检查。

这部分的关键不是“保证模型永远正确”，而是**让错误有界、可发现、可恢复，并且不重复造成损失**。

### 5.3 可观测性：从“看日志”升级为“重建决策过程”

第 5 章把调试拆成 Trace、Metrics、Logs 和 GenAI 事件四类信号。其价值在于：

- 从 Run 到 Thread 的追踪。
- 重建 Agent 的决策路径。
- 回放成功与失败会话。
- 从检查点分叉进行调试。
- 将评估分数嵌入 Span。
- 从真实 trace 生成回放测试。

这意味着日志不仅用于事后查看，还应成为回归测试和故障复现的输入。

### 5.4 安全与合规：把规则放进运行时

第 6 章强调安全策略不能只写在 Prompt 里。公开目录涉及：

- Agent 攻击面分析。
- Production Harness 与运行时强约束。
- 七层纵深防护。
- 约束性部署。
- 框架安全机制比较。
- 数据治理、隐私、透明度、可解释性。
- Compliance-as-Code。

用前端工程师熟悉的方式类比：Prompt 像给页面加提示文案，运行时约束才像服务端鉴权、参数校验和事务边界。前者可以提醒，后者才能真正拦截。

### 5.5 三个实战案例的不同侧重点

- **VLM 视频生产**：观察结果不能只用于最终验收，还要在生成过程中持续纠偏；同时要警惕自反思带来的额外成本和漂移。
- **农业机器人 AgriClaw**：真实世界的传感器会离线，危险操作必须有人机协同和中断机制，不能假设环境永远可信。
- **CyberOps 代码修复**：Agent 与计算机的交互界面、部署者与监控者的分工，以及多 Agent 共识机制，决定了自治系统能否安全运行。

## 9. 第 10 章的三条设计哲学

官方目录明确列出：

1. **简单胜于复杂。**
2. **状态机优于无限循环。**
3. **接口即性能。**

结合全书主题，可以理解为：架构应优先保证可控性；任务状态应显式存在；工具接口的质量会直接影响整个 Agent 的稳定性、延迟和可调试性。

## 10. 工程检查清单

以下清单是根据公开目录主题整理，不是书中原文：

### 执行与预算

- [ ] 每一步是否有明确的最大步数、时间和 token 预算？
- [ ] 循环检测与停止条件是否独立于模型意愿？
- [ ] 重试是否有次数、退避和总时限？
- [ ] 失败后是否会降级，而不是继续放大调用？

### 状态与恢复

- [ ] 待处理请求是否也是持久化状态？
- [ ] 副作用发生前是否先记录执行意图？
- [ ] 恢复时是否核对每个状态边界，而不只核对末态？
- [ ] 无法证明是否执行成功的动作，是否拒绝自动重放？

### 幂等与补偿

- [ ] 下单、扣款、发送消息等动作是否有稳定幂等键？
- [ ] 非幂等动作超时后是否进入明确的人工处理或失败状态？
- [ ] 不可逆错误是否有补偿事务或回滚方案？

### 观测与验证

- [ ] 是否能从 trace 还原模型看到了什么、决定什么、执行了什么？
- [ ] 是否能重放一次真实失败并生成回归测试？
- [ ] 评估是否区分 Session、Trace 和 Span 层级？
- [ ] “系统显示成功”是否有独立证据证明任务真的完成？

### 安全与权限

- [ ] 工具是否遵循最小权限原则？
- [ ] 高危动作是否需要人工确认？
- [ ] 安全策略是否由运行时强制执行？
- [ ] 未认证或中断的结果是否明确标记 `certified: false`？

| 防止重复副作用 | 动作执行前先持久化 inFlight；无法确认完成时停止为 interrupted，不自动重试。 |
| 确定性恢复 | 以 seed 和成功动作重建世界，并核对初始及每个 StepRecord 的 stateHash。 |
| 回放测试 Harness | `verify/replay.ts`、预测对照审计和独立复核脚本。 |
| 进行中信息边界 | start、step、status、resource 不返回 mutant、coverage、内部状态和 detection。 |
| 运行时约束 | 输出根守卫、最大步数、墙钟、磁盘活跃局上限、进程内队列和跨进程文件锁。 |
| 安全失败 | 死者锁 fail-closed；中断局逐出口写 `certified:false`。 |

重合度最高的章节是第 4 章“执行可靠性”和第 5 章“调试与排查”。如果后续继续扩展项目，优先可以对照检查的是：长任务预算治理、更细粒度的幂等设计、Span 级评估，以及部署侧的隔离与监控。
